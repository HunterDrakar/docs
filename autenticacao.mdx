Toda requisição leva a chave da clínica no header `Authorization`:

```http
Authorization: Bearer elim_live_0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
```

A chave identifica a **clínica**. Tudo o que a API devolve é da clínica dona da chave, e nada mais: um `run_id` de outra clínica responde `404`, exatamente como um id inexistente.

## Como obter a chave

1. A equipe do Elim habilita a **API Pública** para a clínica.
2. Em **Configurações → API**, gere a chave. O valor completo aparece **uma única vez**. O Elim guarda só um hash; se a chave se perder, é preciso gerar outra.
3. Guarde a chave num cofre de segredos ou variável de ambiente. Nunca em código-fonte, repositório, planilha ou mensagem.

<Warning>
  Só existe **uma chave ativa por clínica**. Gerar uma nova revoga a anterior no mesmo instante (a nova herda os escopos da anterior): o sistema que usava a antiga passa a receber `401` imediatamente. Troque a chave no seu sistema antes de gerar a nova, ou faça a troca num horário sem disparos.
</Warning>

## Formato

A chave começa com um prefixo seguido de 64 caracteres hexadecimais (minúsculos). O prefixo permite identificar a chave nos logs e na tela do Elim sem expor o segredo.

| Prefixo | Onde vale |
| --- | --- |
| `elim_live_` | **Produção** (`www.elimagenda.com.br`). É a única aceita lá. |
| `elim_test_` | **Só no ambiente de testes do Elim**, com dados de teste. O endereço do ambiente de testes é informado pelo Elim junto com a chave. |

Uma chave `elim_test_` enviada à produção responde `401 ERR_INVALID_KEY`, como qualquer chave inválida, e vice-versa. Desenvolva e teste a integração com a chave de teste, e troque pela `elim_live_` da clínica só para ir ao ar.

## Escopos

Além de identificar a clínica, a chave tem **escopos**: o que ela pode ver e fazer. A clínica marca os escopos na aba API, e regenerar a chave mantém os escopos da anterior. Rota sem o escopo necessário responde `403 ERR_SCOPE_MISSING`. Veja [Escopos e compartilhamento](/escopos).

## Erros de acesso

| HTTP | Código | O que aconteceu |
| --- | --- | --- |
| `401` | `ERR_INVALID_KEY` | Header ausente, malformado, chave inexistente ou revogada. A resposta é a mesma em todos esses casos, de propósito. |
| `403` | `ERR_FEATURE_DISABLED` | A chave é válida, mas a API Pública não está habilitada para a clínica ou a clínica está inativa. Fale com o Elim. |
| `403` | `ERR_SCOPE_MISSING` | A chave é válida e a API está liberada, mas falta à chave o escopo que a rota exige. A clínica marca o escopo em Configurações → API. |
| `429` | `ERR_RATE_LIMITED` | Limite de requisições. Veja abaixo. |

## Limites de requisição

Cada rota tem o seu próprio balde por chave: esgotar o limite de uma não afeta as outras.

| Rota | Limite por chave |
| --- | --- |
| `GET /whatsapp/templates`, `GET /whatsapp/numbers`, `GET /whatsapp/runs/{run_id}`, `GET /whatsapp/runs/{run_id}/recipients` | 120 por minuto |
| `POST /whatsapp/messages` | 10 por minuto |
| `GET /events` | 60 por minuto |
| `GET /appointments`, `POST /appointments/search` | 60 por minuto |
| `GET /attendants`, `GET /doctors` | 60 por minuto |
| `GET /availability` | 120 por minuto |
| `POST /patients`, `POST /scheduling-links`, `POST /whatsapp/conversations/search` | 60 por minuto |
| **Por endereço IP, toda a API** | 300 por minuto |

Quando o limite é atingido, a resposta `429` traz:

```http
Retry-After: 37
X-RateLimit-Limit: 120
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1756800037
```

`Retry-After` é em segundos. `X-RateLimit-Reset` é o instante em que o balde esvazia, em segundos desde a época Unix. Espere o `Retry-After` antes de tentar de novo; insistir só mantém o balde cheio.

<Note>
  O limite é contado por instância do servidor, então o valor efetivo pode ser um pouco maior que o da tabela. Trate os números como um freio, não como uma cota que você pode consumir até o último pedido.
</Note>

## Boas práticas

- **Um cliente HTTP, uma chave.** Não distribua a chave para sistemas diferentes; cada um que precisa de acesso deveria passar pelo seu backend.
- **Rotacione ao trocar de fornecedor** ou quando alguém que tinha acesso sair da equipe.
- **Nunca envie a chave em query string.** Só no header `Authorization`.
- **Trate `401` como definitivo.** Repetir a requisição com a mesma chave não vai funcionar. Alerte alguém.
